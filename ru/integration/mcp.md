# MCP-сервер

## Зачем нужен MCP

MCP (Model Context Protocol) — это открытый протокол, по которому ИИ-агенты (например, ассистенты на базе больших языковых моделей) получают структурированный доступ к данным и инструментам внешних систем. Вместо того чтобы «угадывать» структуру системы, агент запрашивает у MCP-сервера описанные ресурсы (данные только для чтения) и инструменты (действия, которые можно выполнить), а сервер возвращает результат в машинно-читаемом виде.

BaSYS включает встроенный MCP-сервер, который открывает агенту доступ к метаданным конкретной базы (тенанта). С его помощью агент может прочитать список типов данных и видов метаобъектов, проверить корректность описания объекта метаданных по встроенной JSON-схеме и импортировать пакет метаданных в базу. Это позволяет автоматизировать рутинные задачи конфигурирования: агент сам выгружает текущее состояние, формирует изменения и загружает их обратно, не собирая бинарный архив вручную.

MCP-сервер размещён в том же хосте, что и REST API, и использует тот же механизм аутентификации, поэтому для работы с ним не требуется отдельная инфраструктура. Функционально MCP пересекается с [публичным API](publicApi.md): ресурсы MCP — это аналоги read-only эндпоинтов публичного API, но дополнительно MCP предоставляет инструменты, изменяющие метаданные.

## Подключение

Встроенный MCP-сервер доступен по адресу `/mcp` в том же хосте, что и REST API:

```
POST https://<host>/mcp
Authorization: Bearer <access-токен>
Content-Type: application/json
Accept: application/json, text/event-stream
```

| Часть запроса   | Описание                                                                 |
|-----------------|--------------------------------------------------------------------------|
| `<host>`        | Адрес и порт хоста BaSYS (например, `localhost:44365`).                   |
| `<access-токен>`| JWT access-токен, полученный при авторизации.                            |

Особенности подключения:

- **Транспорт** — streamable HTTP в режиме без состояния (stateless). Каждый MCP-вызов выполняется в рамках одного HTTP-запроса, поэтому клиент обязан передавать заголовок `Accept: application/json, text/event-stream`.
- **Аутентификация** — единая с публичным API: тот же JWT-механизм и тот же access-токен. Отдельной процедуры входа для MCP нет. При отсутствии или невалидности токена эндпоинт `/mcp` возвращает `401 Unauthorized`. Полное описание получения и обновления токенов см. в разделе [Авторизация](auth.md).
- **Тенант (база данных)** определяется так же, как и для REST: по claim `DbName` из access-токена. Отдельно имя базы в MCP-запросах передавать не нужно — все вызовы автоматически выполняются в той базе, для которой выпущен токен.

Идентификация сервера:

| Поле        | Значение               |
|-------------|------------------------|
| Имя сервера | `BaSYS Metadata MCP`   |
| Версия      | `0.1.0`                |

> В примерах значения в угловых скобках — это плейсхолдеры, которые нужно подставить под своё окружение: `<host>` — адрес хоста BaSYS, `<access-токен>` — access-токен из ответа авторизации, `<uid>` — идентификатор.

## Ресурсы

Ресурсы MCP доступны только для чтения и возвращают данные в формате `application/json`. Каждый ресурс адресуется собственным URI с префиксом `basys://`. Ресурсы являются аналогами read-only эндпоинтов [публичного API](publicApi.md), но, в отличие от них, возвращают «чистый» JSON без конверта `ResultWrapper`.

| Ресурс                    | URI                                              | Описание                                              |
|---------------------------|--------------------------------------------------|-------------------------------------------------------|
| `data_types`              | `basys://metadata/data-types`                    | Все типы данных текущей базы.                          |
| `meta_object_kinds`       | `basys://metadata/meta-object-kinds`             | Все виды метаобъектов текущей базы.                    |
| `meta_object_kind_by_uid` | `basys://metadata/meta-object-kinds/{uid}`       | Настройки одного вида метаобъекта по идентификатору.   |

### Типы данных

URI: `basys://metadata/data-types`

Возвращает JSON-массив типов данных базы (примитивные и ссылочные типы). Структура каждого элемента совпадает с эндпоинтом [«Типы данных»](publicApi.md#типы-данных) публичного API (`uid`, `kind`, `name`, `title`, `isPrimitive`, `dbType`, `objectKindUid`, `typeName`).

### Виды метаобъектов

URI: `basys://metadata/meta-object-kinds`

Возвращает JSON-массив всех видов метаобъектов базы. Структура элементов совпадает с эндпоинтом [«Список видов метаобъектов»](publicApi.md#список-видов-метаобъектов) публичного API.

### Настройки вида метаобъекта по идентификатору

URI: `basys://metadata/meta-object-kinds/{uid}`

| Параметр | Расположение | Описание                                          |
|----------|--------------|---------------------------------------------------|
| `uid`    | URI          | Уникальный идентификатор вида метаобъекта (GUID).  |

Возвращает подробные настройки одного вида метаобъекта. Структура совпадает с эндпоинтом [«Настройки вида метаобъекта по идентификатору»](publicApi.md#настройки-вида-метаобъекта-по-идентификатору) публичного API.

## Инструменты

Инструменты (tools) — это действия, которые агент может выполнить на сервере. В отличие от ресурсов, инструмент `import_metadata` способен изменять метаданные базы. Результат каждого инструмента возвращается в виде компактного JSON-объекта (поля в `camelCase`).

| Инструмент          | Назначение                                                                 |
|---------------------|----------------------------------------------------------------------------|
| `validate_metadata` | Проверка одного объекта метаданных по встроенной JSON-схеме (без записи в базу). |
| `import_metadata`   | Импорт пакета метаданных (полный или частичный) в текущую базу.            |

### validate_metadata

Проверяет один объект метаданных на соответствие встроенной JSON-схеме. Это лёгкая офлайн-проверка формы объекта: она **не** обращается к базе данных и **не** гарантирует успешный импорт (существование вида, конфликты версий и проверки манифеста не выполняются). Чтобы проверить реальную загрузку, используйте `import_metadata` с `dryRun = true`.

Параметры:

| Параметр     | Тип    | Описание                                                                 |
|--------------|--------|--------------------------------------------------------------------------|
| `schemaType` | enum   | Вид объекта метаданных, задающий используемую JSON-схему (см. таблицу ниже). |
| `content`    | string | Исходный JSON-текст одного объекта метаданных (не архив и не пакет).     |

Допустимые значения `schemaType`:

| Значение          | Описание                                                                 |
|-------------------|--------------------------------------------------------------------------|
| `MetaObject`      | Сохраняемые настройки метаобъекта (справочник, документ, регистр и т. п.). |
| `DataView`        | Настройки представления данных, включая показатели.                       |
| `Menu`            | Настройки меню приложения.                                                |
| `Workflow`        | Настройки бизнес-процесса, включая шаги.                                  |
| `ExcelReport`     | Настройки Excel-отчёта.                                                   |
| `PrintForm`       | Настройки печатной формы.                                                 |
| `ConstructorForm` | Настройки формы конструктора.                                            |

Результат:

| Поле         | Тип     | Описание                                                                 |
|--------------|---------|--------------------------------------------------------------------------|
| `isValid`    | bool    | `true`, если объект соответствует схеме.                                  |
| `schemaType` | string  | Схема, по которой выполнялась проверка.                                   |
| `errorCount` | int     | Общее число найденных ошибок (даже если в `errors` попала только часть).  |
| `errors`     | array   | Список ошибок валидации (число элементов может быть ограничено).         |

Каждый элемент массива `errors` имеет структуру:

| Поле      | Тип    | Описание                                                          |
|-----------|--------|-------------------------------------------------------------------|
| `path`    | string | JSON-путь к проблемному узлу (или маркер корня).                  |
| `kind`    | string | Вид ошибки валидации (например, `PropertyRequired`, `StringExpected`). |
| `message` | string | Человекочитаемое описание ошибки.                                |

Пример результата (объект корректен):

```json
{
  "isValid": true,
  "schemaType": "MetaObject",
  "errorCount": 0,
  "errors": []
}
```

Пример результата (найдена ошибка):

```json
{
  "isValid": false,
  "schemaType": "MetaObject",
  "errorCount": 1,
  "errors": [
    {
      "path": "#/name",
      "kind": "PropertyRequired",
      "message": "PropertyRequired at '#/name'."
    }
  ]
}
```

### import_metadata

Импортирует пакет метаданных в текущую базу. Агент передаёт набор текстовых файлов (путь + содержимое), включая исходный `manifest.json`, полученный при предыдущей выгрузке. Инструмент сам собирает zip-архив в памяти, поэтому строить бинарный архив вручную не требуется.

Частичный импорт выполняется просто: достаточно отправить только изменённые файлы вместе с манифестом.

Параметры:

| Параметр               | Тип     | По умолчанию | Описание                                                                                   |
|------------------------|---------|--------------|--------------------------------------------------------------------------------------------|
| `files`                | array   | —            | Файлы пакета (`path` + `content`). Один из файлов обязательно `manifest.json`.             |
| `dryRun`               | bool    | `true`       | При `true` вычисляется только план импорта, запись в базу не производится.                  |
| `allowConflictOverride`| bool    | `false`      | При `true` объект перезаписывается, даже если его версия в базе больше версии в манифесте.  |
| `allowModifiedEntries` | bool    | `true`       | При `true` применяются записи, содержимое которых отличается от хеша, указанного в манифесте.|

Каждый элемент массива `files` имеет структуру:

| Поле      | Тип    | Описание                                                                                   |
|-----------|--------|--------------------------------------------------------------------------------------------|
| `path`    | string | Относительный путь файла внутри пакета (например, `manifest.json` или `Catalog/Goods/Catalog.Goods.json`). Прямые и обратные слеши допускаются и приводятся к прямым. |
| `content` | string | Исходное текстовое содержимое файла в UTF-8.                                               |

Ограничения и проверки:

- В наборе обязательно должен присутствовать файл `manifest.json` (взятый из предыдущей выгрузки).
- Суммарный размер содержимого файлов не должен превышать **64 МиБ** (измеряется до сжатия).
- Пути файлов проверяются на безопасность: абсолютные пути и переходы вверх по дереву (`..`) отклоняются.

Результат:

| Поле           | Тип    | Описание                                                                                   |
|----------------|--------|--------------------------------------------------------------------------------------------|
| `isSuccess`    | bool   | `true`, если импорт (или пробный прогон) завершился без ошибки верхнего уровня.             |
| `message`      | string | Сообщение о статусе или ошибке.                                                            |
| `summary`      | object | Сводные счётчики плана импорта (см. ниже).                                                  |
| `items`        | array  | Результат по каждому объекту (см. ниже).                                                    |
| `manifestDiff` | array  | Обновлённые записи манифеста для созданных/изменённых объектов. Их нужно слить с локальным манифестом перед следующей частичной загрузкой. |

Структура `summary`:

| Поле                  | Тип  | Описание                                                          |
|-----------------------|------|-------------------------------------------------------------------|
| `totalEntries`        | int  | Всего записей в пакете.                                           |
| `created`             | int  | Будет создано / создано объектов.                                |
| `updated`             | int  | Будет обновлено / обновлено объектов.                            |
| `skippedNoChange`     | int  | Пропущено, так как содержимое не изменилось.                     |
| `skippedConflict`     | int  | Пропущено из-за конфликта версий.                                |
| `skippedKindFiltered` | int  | Пропущено из-за фильтрации по виду.                              |
| `failed`              | int  | Завершилось ошибкой.                                             |
| `dryRun`              | bool | Признак пробного прогона.                                        |

Каждый элемент массива `items` имеет структуру:

| Поле                 | Тип    | Описание                                                                              |
|----------------------|--------|---------------------------------------------------------------------------------------|
| `path`               | string | Путь записи в пакете.                                                                 |
| `kindName`           | string | Имя вида метаобъекта (если определено).                                               |
| `name`               | string | Имя объекта (если определено).                                                        |
| `action`             | string | Действие плана: `Created`, `Updated`, `SkippedNoChange`, `SkippedConflict`, `SkippedKindFiltered` или `Failed`. |
| `reason`             | string | Причина (для пропусков и ошибок).                                                     |
| `modifiedSinceExport`| bool   | `true`, если содержимое записи отличается от хеша, указанного в манифесте.            |

> Рекомендуемый порядок работы: сначала выполните `import_metadata` с `dryRun = true`, чтобы получить план импорта и убедиться в отсутствии конфликтов, и только затем повторите вызов с `dryRun = false` для фактической записи. После реального импорта слейте полученный `manifestDiff` с локальным манифестом — иначе при следующей частичной загрузке актуальные версии будут восприняты как конфликты.

Пример результата (пробный прогон):

```json
{
  "isSuccess": true,
  "message": "OK",
  "summary": {
    "totalEntries": 2,
    "created": 1,
    "updated": 1,
    "skippedNoChange": 0,
    "skippedConflict": 0,
    "skippedKindFiltered": 0,
    "failed": 0,
    "dryRun": true
  },
  "items": [
    {
      "path": "Catalog/Goods/Catalog.Goods.json",
      "kindName": "Catalog",
      "name": "Goods",
      "action": "Updated",
      "reason": null,
      "modifiedSinceExport": true
    }
  ],
  "manifestDiff": []
}
```

## Обработка ошибок

MCP-сервер разделяет ошибки на два уровня:

| Уровень            | Признак                          | Как обрабатывать                                                                 |
|--------------------|----------------------------------|----------------------------------------------------------------------------------|
| Транспорт / доступ | HTTP `401` на эндпоинте `/mcp`   | Токен отсутствует, недействителен или истёк. Обновите access-токен через refresh и повторите запрос (см. [Авторизация](auth.md)). |
| Прикладной         | `isSuccess: false` / `isValid: false` | Вызов выполнен, но операция завершилась ошибкой. Причина — в поле `message` (для `import_metadata`) или в массиве `errors` (для `validate_metadata`). |

> Инструменты не возвращают технические детали и стек вызовов: при непредвиденной ошибке агент получает общее сообщение, а подробности записываются в журнал сервера.
