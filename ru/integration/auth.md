# Авторизация

Публичный API BaSYS и встроенный MCP-сервер используют единый механизм аутентификации на основе JWT-токенов (JSON Web Token). Клиент один раз передаёт логин и пароль, получает пару токенов (access + refresh) и далее работает по короткоживущему access-токену, периодически обновляя его через refresh-токен.

Аутентификация выполняется в контексте конкретной базы данных (тенанта): имя базы является частью маршрута при получении токена и зашивается в сам токен в виде claim `DbName`. Благодаря этому последующие запросы автоматически выполняются в нужной базе без передачи её имени.

## Общая схема работы

1. Клиент отправляет логин, пароль и имя базы на эндпоинт получения токена.
2. Сервер проверяет учётные данные и возвращает access-токен, refresh-токен и время истечения access-токена.
3. Клиент передаёт access-токен в заголовке `Authorization: Bearer <token>` при каждом обращении к публичному API или MCP.
4. Когда access-токен истекает, клиент обменивает refresh-токен на новую пару токенов, не запрашивая логин и пароль повторно.
5. Когда истекает refresh-токен, клиент проходит аутентификацию заново по логину и паролю.

## Получение токена

Запрос обменивает учётные данные пользователя на пару токенов.

```
POST /api/public/v1/auth/{dbName}
Content-Type: application/json
```

| Параметр   | Расположение | Описание                                          |
|------------|--------------|---------------------------------------------------|
| `dbName`   | маршрут      | Имя базы данных (тенанта), к которой выполняется вход. |
| `login`    | тело         | Логин пользователя (email).                       |
| `password` | тело         | Пароль пользователя.                              |

Тело запроса:

```json
{
  "login": "<login>",
  "password": "<password>"
}
```

Пример запроса:

```bash
curl -X POST https://<host>/api/public/v1/auth/<dbName> \
  -H "Content-Type: application/json" \
  -d '{ "login": "<login>", "password": "<password>" }'
```

> В примерах значения в угловых скобках — это плейсхолдеры, которые нужно подставить под своё окружение: `<host>` — адрес и порт хоста BaSYS (например, `localhost:44365`), `<dbName>` — имя базы данных, `<login>` и `<password>` — учётные данные пользователя, `<access-токен>` и `<refresh-токен>` — значения из ответа.

В случае успеха возвращается код `200 OK` и тело со структурой токенов:

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expiresAtUtc": "2026-06-29T11:20:00Z"
}
```

| Поле           | Тип      | Описание                                                                 |
|----------------|----------|--------------------------------------------------------------------------|
| `token`        | string   | Access-токен. Передаётся в заголовке `Authorization` при каждом запросе. |
| `refreshToken` | string   | Refresh-токен. Используется для обновления access-токена.                |
| `expiresAtUtc` | datetime | Момент истечения access-токена в UTC.                                    |

Возможные ошибки:

| Код  | Причина                                                              |
|------|----------------------------------------------------------------------|
| `400` Bad Request   | Не указано имя базы данных (`dbName`).                 |
| `401` Unauthorized  | Неверный логин или пароль.                            |

## Использование access-токена

Полученный access-токен передаётся в каждом запросе к публичному API в заголовке `Authorization` со схемой `Bearer`:

```bash
curl https://<host>/api/public/v1/metadata/meta-objects/<kind> \
  -H "Authorization: Bearer <access-токен>"
```

Имя базы данных в запросах к API повторно указывать не нужно: оно берётся из claim `DbName` внутри access-токена, поэтому запрос автоматически выполняется в той базе, для которой был выпущен токен.

> Все защищённые эндпоинты публичного API требуют именно JWT-схему аутентификации (`Bearer`). Cookie-аутентификация, используемая веб-интерфейсом платформы, на публичный API не распространяется.

## Аутентификация в MCP

Встроенный MCP-сервер размещён в том же хосте, что и REST API, по адресу `/mcp` и защищён тем же JWT-механизмом. Отдельной процедуры входа для MCP нет — используется тот же access-токен, что и для публичного API.

MCP-клиент (например, ИИ-агент) должен подключаться к эндпоинту со следующими заголовками:

```
POST /mcp
Authorization: Bearer <access-токен>
Content-Type: application/json
Accept: application/json, text/event-stream
```

Особенности подключения:

- Транспорт — streamable HTTP в режиме без состояния (stateless), поэтому клиент обязан передавать `Accept: application/json, text/event-stream`.
- Тенант (база данных) для MCP-вызовов определяется так же, как и для REST: по claim `DbName` из access-токена. Отдельно имя базы в MCP-запросах не передаётся.
- При отсутствии или невалидности токена эндпоинт `/mcp` возвращает `401 Unauthorized`.

## Обновление токена (refresh)

Когда access-токен истёк или близок к истечению, новую пару токенов можно получить, не запрашивая логин и пароль, — обменяв refresh-токен.

```
POST /api/public/v1/auth/refresh/{dbName}
Content-Type: application/json
```

| Параметр       | Расположение | Описание                                         |
|----------------|--------------|--------------------------------------------------|
| `dbName`       | маршрут      | Имя базы данных, которой принадлежит refresh-токен. |
| `refreshToken` | тело         | Ранее выданный refresh-токен.                    |

Тело запроса:

```json
{
  "refreshToken": "<refresh-токен>"
}
```

Пример запроса:

```bash
curl -X POST https://<host>/api/public/v1/auth/refresh/<dbName> \
  -H "Content-Type: application/json" \
  -d '{ "refreshToken": "<refresh-токен>" }'
```

В случае успеха возвращается код `200 OK` и **новая пара** токенов в том же формате, что и при получении токена (`token`, `refreshToken`, `expiresAtUtc`).

Возможные ошибки:

| Код  | Причина                                                                       |
|------|-------------------------------------------------------------------------------|
| `400` Bad Request   | Не указано имя базы данных (`dbName`).                         |
| `401` Unauthorized  | Refresh-токен недействителен, истёк или не принадлежит указанной базе. |

### Как сервер проверяет refresh-токен

При обновлении сервер выполняет несколько проверок refresh-токена:

- **Подпись.** Access- и refresh-токены подписываются разными ключами. Refresh-токен проверяется отдельным ключом (`Jwt:RefreshTokenKey`); access-токен в роли refresh-токена использовать нельзя.
- **Срок действия.** Токен с истёкшим claim `exp` отклоняется.
- **Тип токена.** Внутри refresh-токена присутствует claim `token_type` со значением `refresh`. Токен без этого признака (в частности, обычный access-токен) к обмену не принимается.
- **Принадлежность базе.** Claim `DbName` внутри токена должен совпадать с именем базы из маршрута (сравнение без учёта регистра). Refresh-токен одной базы нельзя использовать для другой.

Любая непройденная проверка приводит к ответу `401 Unauthorized`.

## Время жизни токенов и настройки

Сроки жизни токенов и ключи подписи задаются в конфигурации хоста (секция `Jwt`):

| Параметр                     | Назначение                                              | Значение по умолчанию |
|------------------------------|---------------------------------------------------------|-----------------------|
| `Jwt:TokenKey`               | Ключ подписи access-токена.                             | —                     |
| `Jwt:RefreshTokenKey`        | Ключ подписи refresh-токена (отличается от access).     | —                     |
| `Jwt:JwtExpiresMinutes`      | Время жизни access-токена, мин.                         | `60` (1 час)          |
| `Jwt:JwtRefreshExpiresMinutes` | Время жизни refresh-токена, мин.                      | `43200` (30 дней)     |

Идея разделения такова: access-токен короткоживущий и используется для всех запросов, а refresh-токен живёт долго и применяется только для получения новых access-токенов.

> Токены проверяются по подписи и сроку действия и не хранятся на сервере. Поэтому access- и refresh-токены действуют до истечения своего срока, а обновление выдаёт новую пару, не влияя на ранее выданные токены. Управляйте сроком действия токенов через настройки секции `Jwt`.

## Общие практики работы с токенами

Рекомендации по безопасной и надёжной работе с JWT-аутентификацией:

- **Используйте только HTTPS.** Токены передаются в заголовках в открытом виде, и перехват любого из них даёт доступ к API. Не передавайте токены в параметрах URL.
- **Храните токены безопасно.** Access- и особенно долгоживущий refresh-токен следует держать в защищённом хранилище (серверный секрет-менеджер, защищённое хранилище ОС), а не в логах, исходном коде или общедоступных файлах.
- **Обновляйте заранее.** Ориентируйтесь на поле `expiresAtUtc` и запрашивайте новую пару немного раньше истечения access-токена, а не дожидайтесь ошибки. Это исключает «провалы» в обслуживании запросов.
- **Обрабатывайте `401` как сигнал к обновлению.** Если запрос к API вернул `401`, выполните один цикл обновления через refresh-токен и повторите запрос. Если обновление тоже вернуло `401` — refresh-токен истёк, и нужна повторная аутентификация по логину и паролю.
- **Избегайте параллельных обновлений.** При нескольких одновременных запросах синхронизируйте обновление токена (мьютекс/single-flight), чтобы не запускать несколько процедур refresh одновременно.
- **Не декодируйте токен как доверенный источник прав на клиенте.** Содержимое JWT (например, claim `DbName` или `exp`) можно читать для удобства, но решения о доступе принимает сервер при проверке подписи.
